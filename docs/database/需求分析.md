# 网上综合书店销售数据库项目  
## 第一阶段：需求分析（数据库负责人）
> 文档用途：用于小组协作与后续 ER 图、表结构设计输入
---
## 1. 项目背景与分析目标
网上综合书店业务覆盖门店销售、图书商品、供应链协作、客户会员运营等场景。  
数据库是系统底座，需要先明确“对象是什么、对象如何关联、业务规则如何落地”。
本阶段需求分析目标：
- 提取核心实体、属性与关系；
- 识别子类实体与多对多关系；
- 明确关键业务规则与数据约束；
- 为下一阶段 ER 图与表结构设计提供直接依据。
---
## 2. 业务范围与边界
### 2.1 业务范围（In Scope）
| 模块 | 业务内容 | 数据关注点 |
|---|---|---|
| 门店管理 | 维护连锁门店信息 | 门店名称、城市、地址、电话、负责人 |
| 供应商管理 | 维护供货商及供货关系 | 供应商名称、联系人、电话、邮箱、合作状态 |
| 商品管理 | 维护可销售商品 | 商品名称、分类、计量单位、售价、库存、在售状态 |
| 图书管理 | 管理图书专有信息 | ISBN、出版社、作者、译者、版次、页数 |
| 出版社管理 | 维护出版社信息 | 名称、联系人、电话、邮箱、地址 |
| 客户会员管理 | 管理客户与会员体系 | 客户姓名、联系方式、地址、会员等级、积分 |
| 销售管理 | 记录交易过程 | 销售主单、销售明细、支付方式、金额 |
| 统计分析支撑 | 为报表提供数据基础 | 销量、销售额、会员消费、商品热度 |
### 2.2 暂不纳入（Out of Scope）
当前阶段不重点覆盖：
- 库存调拨与仓储作业细节；
- 复杂促销引擎（满减、优惠券、阶梯折扣）；
- 退款/退货全流程；
- 物流配送履约系统。

## 3. 核心实体识别
### 3.1 主实体清单
| 实体名 | 中文含义 | 设计定位 |
|---|---|---|
| `Store` | 门店 | 销售发生地点 |
| `Supplier` | 供应商 | 商品供货主体 |
| `Category` | 商品分类 | 商品归类体系 |
| `Product` | 商品 | 通用可售卖对象 |
| `Book` | 图书 | 商品子类（图书特有字段） |
| `Publisher` | 出版社 | 图书出版主体 |
| `Customer` | 客户 | 消费行为主体 |
| `Member` | 会员 | 客户子类（积分等级） |
| `Sale` | 销售单 | 交易主记录 |
| `Sale_Item` | 销售明细 | 交易明细记录 |
| `Author` | 作者 | 图书创作者 |
| `Translator` | 译者 | 图书译者 |
### 3.2 辅助/中间实体
| 实体名 | 作用 | 解决关系 |
|---|---|---|
| `Supplier_Product` | 记录供货关系属性 | `Supplier` ↔ `Product` 多对多 |
| `Book_Author` | 记录图书作者关系 | `Book` ↔ `Author` 多对多 |
| `Book_Translator` | 记录图书译者关系 | `Book` ↔ `Translator` 多对多 |

## 4. 子类实体分析
采用“父类 + 子类”建模，减少冗余并满足 3NF。
| 父类 | 子类 | 原因 |
|---|---|---|
| `Product` | `Book` | 只有图书才有 ISBN、出版社、页数等字段 |
| `Customer` | `Member` | 会员一定是客户，但客户不一定是会员 |
### 4.1 设计说明
- `Book` 与 `Product` 采用 1:1（共享主键）；
- `Member` 与 `Customer` 采用 1:1（可选子类）；
- 该方案可避免在 `Product` 或 `Customer` 中出现大量仅部分记录有效的空字段。
---
## 5. 关系与业务语义分析
### 5.1 主要关系基数
| 关系 | 基数 | 业务含义 |
|---|---|---|
| `Store` -> `Sale` | 1 : N | 一个门店产生多笔销售 |
| `Customer` -> `Sale` | 1 : N（可空） | 客户可多次购买，销售可为散客 |
| `Sale` -> `Sale_Item` | 1 : N | 一笔销售包含多条明细 |
| `Product` -> `Sale_Item` | 1 : N | 商品可出现在多笔明细中 |
| `Category` -> `Product` | 1 : N | 一个分类下有多个商品 |
| `Supplier` <-> `Product` | N : N | 多供应商供同商品、同供应商供多商品 |
| `Product` -> `Book` | 1 : 0..1 | 仅图书类商品才有 `Book` 记录 |
| `Publisher` -> `Book` | 1 : N | 一个出版社可出版多本书 |
| `Book` <-> `Author` | N : N | 一本书可多作者 |
| `Book` <-> `Translator` | N : N | 一本书可多译者或无译者 |
| `Customer` -> `Member` | 1 : 0..1 | 客户可升级为会员 |

## 6. 关键业务规则
### 6.1 基础规则
1. 商品必须属于某个分类。  
2. 图书必须具备唯一 ISBN。  
3. 一笔销售必须绑定门店。  
4. 一笔销售至少包含一条明细。  
5. 会员必须基于已有客户建立。  
### 6.2 数据一致性规则
1. 销售明细保存成交时单价快照，不受后续商品调价影响。  
2. 供应关系记录供货价、是否主供、起订量等业务属性。  
3. 图书与作者/译者关系通过中间表维护，避免重复字段。  
4. 商品库存用于记录当前可售数量，支持后续销售扣减与补货更新。  
5. 供应商合作状态与商品在售状态分别维护，用于业务管理与查询筛选。  
### 6.3 合法值规则（建议数据库层约束）
| 字段类型 | 规则 |
|---|---|
| 价格字段 | `> 0` |
| 库存字段 | `>= 0` |
| 销售数量字段 | `> 0` |
| 金额字段 | `>= 0` |
| 积分字段 | `>= 0` |
| 必填业务字段 | `NOT NULL` |
| 唯一业务字段（如 ISBN） | `UNIQUE` |

## 8. 数据库设计原则（本项目约定）
### 8.1 规范性
- 满足第三范式（3NF）；
- 消除重复依赖与传递依赖；
- 使用主外键确保引用完整性。
### 8.2 可读性
- 统一使用 `snake_case` 命名；
- 主键命名统一 `xxx_id`；
- 中间表命名统一 `a_b`。
### 8.3 可扩展性
- 支持后续增加新商品子类（如文创、电子书）；
- 支持新增营销、库存、报表模块而不重构主干模型。
