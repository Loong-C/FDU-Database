# 网上综合书店销售数据库项目 README
https://github.com/Loong-C/FDU-Database.git
## 1. 项目概述

本项目旨在设计并实现一个 **网上综合书店销售数据库系统**，用于支持连锁销售公司的日常经营与信息管理。系统需要覆盖以下核心对象与业务：

- 门店（Store）管理
- 供货商（Supplier）管理
- 商品（Product）管理
- 图书（Book）管理
- 出版社（Publisher）管理
- 客户（Customer）与会员（Member）管理
- 销售记录（Sale）管理
- 销售数据统计与分析

本项目不仅是一个数据库建模任务，还应实现一个可交互的 Web 系统，并配套演示文稿与用户手册。

## 3. 每个人的详细工作要求

### 3.1 数据库负责人工作要求

数据库负责人是整个项目的基础角色，因为后端接口和部分前端页面都依赖数据库结构。

#### 需要完成的任务

1. **需求拆解**
   - 从题目中提取实体、属性、关系、业务规则。
   - 明确哪些是普通实体，哪些是子类实体。
   - 明确多对多关系需要通过哪些中间表实现。

2. **ER 图设计**
   - 至少包含以下实体：
     - Store
     - Supplier
     - Product
     - Book
     - Customer
     - Member
     - Sale
     - Publisher
   - 补充必要的辅助实体，例如：
     - Category（商品类别）
     - Supplier_Product（供货关系表）
     - Book_Author（图书-作者关系表）
     - Book_Translator（图书-译者关系表）

3. **表结构设计**
   - 满足第三范式（3NF）。
   - 明确每张表的：
     - 主键
     - 外键
     - 唯一约束
     - 非空约束
     - 检查约束（如价格大于 0）

4. **编写数据库脚本**
   - `create_database.sql`
   - `create_tables.sql`
   - `data/*.csv`
   - `views_or_reports.sql`（如有统计视图）

5. **准备测试数据**
   - 每个核心表都准备合理示例数据。
   - 销售记录要能支持后续统计分析展示。

6. **撰写数据库设计文档**
   - 表结构说明
   - 字段说明
   - 关系说明
   - 约束说明
   - 设计理由说明

#### 输出标准

- ER 图清晰规范，可直接截图放入 PPT。
- SQL 脚本可在 MySQL/PostgreSQL 中直接运行。
- 所有表命名、字段命名统一。
- 测试数据应覆盖主要业务场景。

#### 建议交付时间

- 第 1 阶段优先完成：需求分析、ER 图、表结构草案
- 第 2 阶段完成：SQL 脚本与测试数据
- 第 3 阶段完成：数据库设计文档整理

### 3.2 后端负责人工作要求

后端负责人负责把数据库能力封装成系统功能，供前端调用。

#### 需要完成的任务

1. **技术选型与项目初始化**
   - 推荐：

     - Java + Spring Boot

   - 根据小组熟悉程度选择，尽量不要用大家都不熟悉的框架。

2. **数据库连接配置**
   - 连接数据库并完成基本 CRUD 操作。
   - 封装数据库访问逻辑。

3. **实现核心模块接口**
   - 门店管理接口
   - 供货商管理接口
   - 商品管理接口
   - 图书管理接口
   - 客户管理接口
   - 会员管理接口
   - 销售记录管理接口
   - 统计分析接口

4. **接口建议**
   - 查询列表
   - 查询详情
   - 新增记录
   - 修改记录
   - 删除记录
   - 统计汇总接口（按门店、商品类别、时间等维度）

5. **业务逻辑实现**

   - 输出接口测试结果。

   - 路径
   - 请求方式
   - 请求参数
   - 返回格式

#### 输出标准

- 后端代码能够正常启动。
- 所有主要功能至少有基础接口可用。
- 接口命名风格统一。
- 错误提示清晰。

#### 建议交付时间

- 数据库结构确定后立即开始。
- 应优先完成最基础的 CRUD 接口，再补统计分析功能。

## 8. Git 不是必须，但协作一定要规范

### 8.1 不用 Git 可以吗？

可以，但 **不推荐**。

如果完全不用 Git，你们也能完成项目，但需要非常严格地管理文件版本，否则很容易出现：

- 同一个文件被两个人同时改，互相覆盖
- 不知道哪个版本是最新版本
- 出现 bug 后找不到是谁改坏的
- 最终汇总时大量冲突

### 8.2 如果暂时不用 Git，替代方案有哪些？

如果你们对 Git 很不熟，可以使用下面的“低门槛协作方案”：

#### 方案 A：共享网盘 + 命名规范

可用工具：
- 腾讯文档 / 金山文档
- 飞书云文档
- 百度网盘共享文件夹
- 微信群文件（不推荐长期用）

操作建议：
- 建一个统一共享文件夹
- 每个人只负责自己的子目录
- 共同文件只允许组长汇总修改
- 文件命名要带日期和版本号，例如：
  - `数据库设计_v1_0415.sql`
  - `前端页面_v2_0416.zip`
  - `PPT初稿_v1_0417.pptx`

#### 方案 B：组长集中汇总制

规则：
- 每个人单独开发自己的部分
- 每天或每两天把最新版本发给组长
- 组长负责合并到总项目中
- 其他成员不要直接改总版本

这个方法适合新手，但缺点是：
- 组长工作量大
- 合并过程容易出错
- 回退版本不方便

#### 方案 C：文档用在线协作，代码分模块单独提交

例如：
- 文档：腾讯文档/飞书在线协作
- 前端：前端负责人单独维护压缩包
- 后端：后端负责人单独维护压缩包
- 数据库：数据库负责人单独维护 SQL
- 最后由组长统一合并

这是一个比完全混放更稳妥的折中方案。

## 9. 如果要用 Git，推荐这样用（适合新手）

如果愿意学一点 Git，其实只需要掌握最基本的一套流程就够了。

### 9.1 为什么建议用 Git

Git 的优势：
- 每次修改都有记录
- 可随时回退旧版本
- 可以多人协作开发
- 便于组长最终统一汇总
- 比“互发压缩包”更不容易乱

### 9.2 推荐协作模式

对于你们这个课程项目，推荐 **最简单的 Git 协作模式**：

- 一个远程仓库（GitHub / Gitee）
- 一个主分支：`main`
- 每个成员一个自己的开发分支：
  - `db-dev`
  - `backend-dev`
  - `frontend-dev`
  - `docs-dev`

组长负责最后合并到 `main`。

## 10. Git 最简工作流程（建议直接照着做）

### 10.1 第一次建立仓库（组长做）

1. 在 GitHub 或 Gitee 创建仓库，例如：
   - `bookstore-db-project`
2. 组长把基础目录结构创建好。
3. 组长提交第一版初始化内容。
4. 组长邀请其他成员加入协作。

---

### 10.2 每个成员第一次获取项目

```bash
git clone 仓库地址
cd bookstore-db-project
```

查看当前分支：

```bash
git branch
```

创建自己的开发分支并切换：

```bash
git checkout -b db-dev
```

其他成员类似：

```bash
git checkout -b backend-dev
git checkout -b frontend-dev
git checkout -b docs-dev
```

第一次推送自己的分支：

```bash
git push -u origin db-dev
```

---

### 10.3 每次开始工作前，先同步最新代码

这是最重要的一步。**不要一打开电脑就直接改。**

先进入项目目录：

```bash
cd bookstore-db-project
```

切换到主分支：

```bash
git checkout main
```

拉取远程最新内容：

```bash
git pull origin main
```

再切回自己的分支：

```bash
git checkout db-dev
```

把主分支最新内容合并到自己的分支：

```bash
git merge main
```

这样做的目的：
- 确保你是在最新版本基础上开发
- 减少后续冲突

---

### 10.4 开始自己的工作

例如数据库负责人修改了 SQL 文件和设计文档。

先看当前状态：

```bash
git status
```

把修改加入暂存区：

```bash
git add .
```

提交本次修改：

```bash
git commit -m "完成数据库表结构与初始化脚本"
```

把自己的分支推送到远程：

```bash
git push origin db-dev
```

---

### 10.5 组长如何汇总成员工作

组长先切换到主分支：

```bash
git checkout main
git pull origin main
```

然后依次合并每个人的分支，例如：

```bash
git merge db-dev
git merge backend-dev
git merge frontend-dev
git merge docs-dev
```

如果没有冲突，就推送：

```bash
git push origin main
```

---

### 10.6 出现冲突怎么办

冲突通常发生在：
- 两个人同时改了同一个文件的同一部分
- 组长合并分支时版本不一致

处理方法：
1. 打开冲突文件。
2. Git 会标记冲突位置。
3. 人工决定保留哪一部分，或者手动整合。
4. 保存文件后重新执行：

```bash
git add .
```

4. **不要直接在 main 分支上乱改。**

## 14. 你们这个项目特别容易遗漏的点

下面这些内容很容易在开发时被忽略，但老师通常会看：

### 14.1 子类实体如何设计

题目要求：
- 图书是商品的子类别
- 会员是客户的子类别

实现时要体现继承关系，例如：
- `product` 存商品公共属性
- `book` 用 `product_id` 或条码作为外键，补充图书特有属性
- `customer` 存客户公共属性
- `member` 用 `customer_id` 关联，补充会员特有属性

### 14.2 多对多关系要落地成中间表

例如：
- 供货商与商品：`supplier_product`
- 图书与作者：`book_author`
- 图书与译者：`book_translator`

### 14.3 销售记录设计要能支持统计

`sale` 表不能只记录“卖了什么”，还要考虑后续统计查询，因此建议包含：
- 销售日期
- 数量
- 单价
- 金额
- 门店编号
- 商品编号
- 客户编号

### 14.4 数据校验不能完全不做

至少应做：
- 电话格式基本校验
- 邮箱格式基本校验
- 数量不能小于等于 0
- 金额不能小于 0
- 出版时间不能晚于当前时间太多
- 删除时检查关联数据

### 14.5 权限管理可以做简化版

老师说要注意权限管理，但课程项目通常不要求做复杂登录系统。你们可以做一个“说明型简化实现”：
- 管理员可维护基础数据
- 普通操作员可录入销售记录
- 查询用户只能查看统计

即使不完整实现，也可以在文档中说明设计思路。

## 19. 当前仓库后端实现说明

当前仓库已按课程项目后端要求补充 Django/DRF 后端工程，并整理为以下结构：

```text
backend/
  accounts/
  analytics/
  catalog/
  common/
  config/
  customers/
  inventory/
  procurement/
  sales/
  stores/
  .env.example
  manage.py
  requirements.txt
sql/
  create_database.sql
  create_tables.sql
  views_or_reports.sql
  data/*.csv
  source/
  tools/
docs/
  api/API接口文档.md
  test/接口测试结果.md
  database/...
README.md
```

### 19.1 后端技术栈

- Python 3.12
- Django 5.2
- Django REST Framework 3.17
- MySQL 8.x
- PyMySQL
- 自实现 JWT 鉴权

### 19.2 后端启动方式

在仓库根目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend\requirements.txt
Copy-Item backend\.env.example backend\.env
cd backend
..\.venv\Scripts\python manage.py bootstrap_business_db --seed --views
..\.venv\Scripts\python manage.py migrate
..\.venv\Scripts\python manage.py seed_demo_users
..\.venv\Scripts\python manage.py runserver
```

注意：
- 实际命令中的 Python 路径应写成 `..\.venv\Scripts\python`
- `backend/.env` 中需要填写真实 MySQL 连接信息
- 首次初始化时需要先执行 `bootstrap_business_db` 创建业务数据库，再执行 `migrate`
- `bootstrap_business_db --seed` 会按外键顺序导入 `sql/data/*.csv`；需要调整演示数据时直接修改对应表的 CSV 即可

### 19.3 已实现的后端模块

- `accounts`：自定义用户、角色、JWT 登录/刷新/登出、用户管理
- `stores`：门店管理接口
- `catalog`：供应商、分类、出版社、作者、译者、商品、图书接口
- `customers`：客户与会员接口
- `inventory`：门店-商品库存列表、库存预警、库存与安全库存调整接口
- `procurement`：采购单、入库单接口，入库审核后增加门店库存
- `sales`：销售主单与明细接口，含库存扣减/回滚
- `analytics`：门店日报、商品排行、会员消费排行、分类汇总接口

### 19.4 已实现的前端模块

- 登录、JWT 刷新、角色菜单与页面级权限控制
- 数据总览与销售分析图表
- 门店、供应商、分类、出版社、作者、译者、商品、图书管理
- 客户、会员、销售订单与新开销售单
- 门店库存、库存预警、采购单、入库单
- 商品/图书表单已按 `inventory(store_id, product_id)` 维护门店库存；销售开单按所选门店库存判断可售数量
